# payment-core 설계 결정 (ADR)

> **이 문서가 무엇인가** — 결제 본체(payment-core)를 **왜 그렇게 정했나**(맥락·대안·trade-off)를 담는 결정 기록(ADR)이다.
> "무엇을 하는가"(구현 진실)는 분리된 [payment-core-spec.md](../spec/payment-core-spec.md)에 둔다.
>
> **대체 관계** — 본 문서와 spec 문서가 `payment-design-v0_2.md`를 대체한다. v0_2는 의사결정 과정을 담은 리뷰 문서로 이력 보존하되, "왜"의 단일 출처는 본 문서다.
>
> **참조 규칙** — spec 본문이 `(근거: D-xx)`로 본 문서의 항목을 가리킨다. **ID·내용 일치는 두 문서의 계약**이다. ID를 바꾸려면 양쪽을 함께 고친다.
>
> **상태 표기** — 모든 결정은 `Accepted`(1차 스코프 확정). 후속 스코프에서 재검토할 항목은 "영향"에 명시한다.
>
> **형식** — 각 ADR = 결정 / 맥락 / 근거 / 대안 / 영향. 출처는 `v0_2 N장`으로 표기.

## D-01 — 결제와 취소를 같은 서버의 별도 모듈로 분리

**결정.** 취소·환불은 결제와 **같은 결제 서버 배포단위 안의 별도 바운디드 컨텍스트/모듈**로 둔다. 별도 서비스로 떼지 않는다. (단, `[2차]` 스코프이며 본 문서는 결제 본체만 다룬다.)

**맥락.** 취소는 결제 데이터(`payments`, `payment_allocation`, 잔액·한도)를 직접 되돌려야 한다. 결제와 취소가 서로 다른 서버·DB에 있으면 원복이 분산 트랜잭션이 된다.

**근거.** 같은 모듈·같은 DB면 취소의 잔액·한도 원복을 **단일 로컬 트랜잭션**으로 처리할 수 있다(2PC 회피). 모듈 경계는 패키지로 유지해 결합도만 낮춘다.

**대안.** ① 취소 전용 마이크로서비스 — 분산 트랜잭션/SAGA 복잡도, 1차 TPS 100엔 과설계. ② 결제·취소를 한 모듈에 합침 — 책임 혼재, 컨텍스트 경계 흐려짐.

**영향.** 1차는 인터페이스 경계만 명시(상태 `PARTIALLY_CANCELLED`/`CANCELLED`, allocation `REFUNDED`, `payment_items` 스키마 보유). 회수 부담은 [[D-09]]와 연결.

## D-02 — 잔액·한도를 payment 서버 내부 모듈로 (별도 서버 X)

**결정.** 잔액(`user_balance`)·일일 한도(`user_daily_usage`/`user_daily_limit`)를 payment 서버 **내부 모듈**로 두고, 결제 트랜잭션과 **같은 DB·같은 트랜잭션**에서 차감한다. (v0_2 2장 "안 B")

**맥락.** 결제 1건은 잔액 차감 + 한도 누적 + 결제 행 생성이 **원자적으로** 일어나야 한다. 일부만 반영되면 잔액·한도 정합성이 깨진다.

**근거.** 내부 모듈이면 한 `@Transactional` 경계 안에서 잔액·한도·결제를 함께 commit/rollback → **원자성 무료**. 동시성도 같은 DB 행 락으로 해결([[D-03]]).

**대안 (v0_2 2장 안 A).** 잔액·한도를 **별도 계정 서버**로 분리 → 결제마다 동기 API 호출 + 분산 트랜잭션(또는 보상). 네트워크 왕복·부분 실패·정합성 복구 비용이 TPS 100 규모에 비해 과도. 확장 시점에 재검토.

**영향.** payment 모듈 안에 `balance` 컨텍스트로 존재. 헥사고날 의존 규칙은 유지(adapter→application→domain). TPS 10000+ 확장 시 잔액 샤딩/분리는 spec 부록 6번·확장 전략으로 이월.

## D-03 — 사용자 동시성은 DB 비관적 락 단독 (Redis 분산 락 없음)

**결정.** 같은 사용자의 동시 요청 직렬화는 `user_balance` row의 `SELECT … FOR UPDATE` **비관적 락 하나**로 한다. Redis 분산 락을 두지 않는다. (v0_2 9장)

**맥락.** 같은 사용자가 동시에 두 결제를 보내면 잔액 이중 차감(lost update)이 날 수 있다. 다중 인스턴스 환경에서도 막아야 한다.

**근거.** `FOR UPDATE`는 DB 레벨 락이라 **인스턴스 수와 무관하게** 직렬화된다. 락 단위가 곧 `user_id`(=PK row)라 경합 범위가 사용자 단위로 최소. Redis 락은 또 하나의 인프라·실패 모드(락 만료/네트워크 분할/이중 획득)를 추가하는데, DB 락으로 이미 충분.

**대안.** ① Redis 분산 락 추가 — 인프라/장애 모드 증가, DB 락과 이중 방어는 1차 규모에 불필요. ② 낙관적 락(`version`) — 경합 시 재시도 폭증, 결제 같은 짧은 임계구역엔 비관적 락이 단순·확실. ③ 원자적 조건부 UPDATE(`UPDATE … SET balance=balance-X WHERE balance>=X`) — 잔액 row **단독**이면 락 보유가 한 문장 길이로 최단이라 더 우수. 그러나 결제는 잔액+한도(다른 row)+이력+결제행이 **한 트랜잭션 원자**여야 하고, 차감 가부 판정을 도메인(`UserBalance`)에 둬 `INSUFFICIENT_BALANCE` 같은 **명확한 에러를 표현**해야 한다([[D-13]]). 조건부 UPDATE는 그 규칙이 SQL `WHERE`로 새고 에러 의미를 잃어 미채택.

**영향.** `user_balance`/`user_daily_usage`에 `version` 컬럼 **없음**(spec 3-3). 락 보유 시간을 짧게 유지해야 하므로 PG 호출을 트랜잭션 밖으로([[D-08]]), 대기 한도는 1초로([[D-07]]). 데드락 회피는 [[D-04]].

## D-04 — 두 row 락은 balance → usage 고정 순서

**결정.** 한 트랜잭션이 `user_balance`와 `user_daily_usage` 두 row를 모두 잠글 때 **항상 `balance` 먼저, `usage` 나중** 순서로 잠근다. `reserve`(결제)와 `compensate`(원복)가 같은 순서를 따른다. (v0_2 9장)

**맥락.** 두 개 이상의 락을 잡는 트랜잭션이 서로 다른 순서로 잡으면 순환 대기 → 데드락.

**근거.** 모든 경로가 동일한 전순서(total order)로만 락을 획득하면 순환 대기가 원천 차단된다(데드락 4조건 중 "순환 대기" 제거). 결제·보상·보정 배치 전부 단일 순서 규칙 하나로 통일.

**대안.** ① 한도·잔액을 한 row로 합쳐 락 1개로 — 도메인 책임 혼합(잔액과 한도는 생명주기·정책이 다름). ② 락 타임아웃 + 재시도로 데드락 흡수 — 비결정적, 사용자 지연 유발.

**영향.** 도메인/애플리케이션 양쪽에 "잔액→한도" 순서 지식이 중복된다 → 주석 교차 참조로 의도를 드러냄. 새 자원 row가 늘면 전순서에 편입해야 한다.

## D-05 — 멱등성 = 클라이언트 키 + UNIQUE(user_id, key) + 테이블 분리

**결정.** 멱등성은 클라이언트가 생성한 `Idempotency-Key`(UUID v4) 헤더로 식별하고, 저장 시 `UNIQUE (user_id, idempotency_key)`로 강제한다. 결제(`payment_idempotency`)와 충전(`charge_idempotency`)은 **테이블을 분리**한다. (v0_2 7장)

**맥락.** 네트워크 재시도·더블 클릭으로 같은 결제 요청이 두 번 올 수 있다. 한 번만 처리하고, 재요청엔 같은 결과를 줘야 한다.

**근거.**
- **클라이언트 키** — 재시도 시 동일 키를 보내야 "같은 요청"임을 서버가 안다. 서버 생성 키로는 재시도를 묶을 수 없다.
- **`(user_id, key)` 복합 UNIQUE** — 키 자체는 클라이언트가 만들어 다른 사용자가 우연히 같은 키를 보낼 수 있다. user_id를 포함해 **사용자 간 충돌·정보 유출**을 차단(보안).
- **테이블 분리** — 결제와 충전은 도메인·상태·payload가 다르다. 한 테이블에 섞으면 분기·인덱스가 복잡.

**대안.** ① 전역 UNIQUE(key) — 사용자 간 키 충돌 가능, 보안상 부적절. ② 단일 멱등성 테이블에 `type` 컬럼 — 결제/충전 흐름 차이를 한 테이블이 떠안아 분기 증가.

**영향.** 진입 시 `(user_id, key)` 조회로 4-3 분기. 행 INSERT 시점엔 `payment_id`/`charge_id`가 NULL(아직 생성 전)이고 같은 트랜잭션에서 채운다. 유효기간은 생성+24h(`expired_at`).

## D-06 — 결제 FAILED 멱등성 행은 신규 재시도 허용

**결정.** 멱등성 `status = FAILED`인 키로 재요청이 오면 **신규 처리를 허용**한다(`PROCEED_NEW`). COMPLETED는 200 재생(REPLAY), PENDING은 409.

**맥락.** PG 거절·잔액 부족 등으로 한 번 실패한 결제를, 사용자가 (충전 후·다른 수단으로) 같은 키로 다시 시도할 수 있다.

**근거.** 실패 원인은 **시간이 지나면 해소 가능**(잔액 충전, 한도 자정 리셋, PG 일시 장애 회복). FAILED를 영구 잠그면 정당한 재시도를 막는다. 반면 COMPLETED·PENDING은 이중 청구 위험이 있어 잠근다.

**대안.** ① FAILED도 영구 잠금 + 새 키 요구 — 클라이언트에 키 재발급 부담, 재시도 UX 저하. ② FAILED 무조건 재생(이전 실패 응답 반환) — 회복된 환경에서도 실패만 돌려줘 결제 불가.

**영향.** 같은 키로 신규 결제 행이 새로 생길 수 있다(이전 FAILED 행은 이력으로 보존). `retry_count`로 추적.

## D-07 — lock_wait 1초 + connectionTimeout 2~3초 + pool 10

**결정.** `innodb_lock_wait_timeout = 1초`, HikariCP `connectionTimeout = 2~3초`, `maximumPoolSize = 10`, 트랜잭션 timeout 10초. (v0_2 9장 보강 9-4·9-8)

**맥락.** 비관적 락([[D-03]]) 경합 시 뒤 요청이 얼마나 기다릴지, 풀이 마르면 얼마나 버틸지의 한도가 필요하다. 기본값(lock_wait 50초, connectionTimeout 30초)은 결제 응답으론 치명적으로 길다. **락 대기와 커넥션 풀은 결합돼 있다** — 락을 기다리는 스레드는 트랜잭션 안에 있어 **커넥션을 점유한 채 블록**되므로, 같은 row 대기자가 N개면 커넥션 N개가 묶인다. 따라서 lock_wait와 pool은 따로 볼 수 없고 함께 짧게/작게 잡는다.

**근거.**
- **lock_wait 1초** — 같은 사용자 동시 결제는 드물고, 임계구역이 수십 ms라 1초면 정상 대기는 흡수하고 비정상 경합은 빠르게 409로 끊는다(사용자에 즉시 재시도 안내).
- **connectionTimeout 2~3초** — 풀 고갈 시 30초 멈춤 대신 빠르게 실패해 스레드·자원 점유를 막는다.
- **pool 10** — TPS 100 + 짧은 트랜잭션엔 10이면 충분. 락 경합을 풀 키우기로 흡수하려 하면 DB 부하만 늘고 경합은 그대로.

**대안.** 기본 타임아웃 유지 — 락/풀 고갈 시 수십 초 응답 지연·스레드 고갈로 장애 전파.

**영향.** 락 대기 초과 → 409 `PAYMENT_IN_PROGRESS`로 매핑. 부하 테스트로 풀 사이즈 재튜닝 여지(고정값 아님).

## D-08 — PG 호출은 트랜잭션 밖 + pg_call_status 별도 commit + 보정 30초/유예 1분

**결정.** 외부 PG 청구는 DB 트랜잭션 **밖**에서 호출한다. 호출 직전 `pg_call_status = CALLING`을 **별도 트랜잭션으로 commit**한다. 응답 불확실(타임아웃)은 `UNKNOWN`으로 두고, `@Scheduled(30초)` + `유예 1분` 보정 배치(ShedLock 분산 단일 실행)가 PG 진실을 재조회해 회복한다. (v0_2 6-3·9장)

**맥락.** PG 호출은 외부 네트워크라 수백 ms~수 초, 게다가 **응답이 유실될 수 있다**(타임아웃 후 실제로는 청구 성공). 이 호출을 DB 트랜잭션 안에 넣으면 락을 그 시간만큼 잡아 동시성이 붕괴된다.

**근거.**
- **트랜잭션 밖 호출** — 락 보유 시간을 수십 ms로 유지([[D-03]] 전제). TX1(예약)·TX2(확정) 사이에 PG 호출을 끼운다.
- **CALLING 별도 commit** — PG 호출 중 서버가 죽으면 메모리 상태가 사라진다. CALLING을 미리 commit해 두면, 보정 배치가 `pg_call_status IN (CALLING, UNKNOWN)`으로 **미완료 호출을 발견**할 수 있다. 같은 트랜잭션에 묶으면 죽을 때 함께 롤백돼 흔적이 사라진다.
- **30초/1분** — 결제 불확실은 사용자 체감 손해(결제됐는지 모름)가 커 빠른 회복을 우선. 1분 유예는 정상 응답이 도착할 시간을 준 뒤 배치가 개입하게 한다.

**대안.** ① PG 호출을 트랜잭션 안에 — 락 장시간 점유로 동시성 붕괴. ② 보정 없이 동기 재시도만 — 타임아웃 후 실제 성공한 청구를 영구히 모름(이중 청구/미반영). ③ 메시지 큐 기반 비동기 확정 — 1차엔 배치로 충분, 인프라 추가 보류.

**영향.** 오케스트레이터 `ProcessPaymentService`는 **`@Transactional` 금지**(불변식). 트랜잭션 경계는 협력자 `PaymentTransactionService`(reserve/markPgCalling/markPgStatus/confirm/compensate)가 잘게 소유. 타임아웃은 원복하지 않고 배치 위임([[D-09]]와 함께 이중 청구 위험 관리).

## D-09 — 보상 시 PG 회수(환불) 실호출 보류, 기록만

**결정.** 보상(TX2 실패·부분 실패)에서 이미 청구된 카드/계좌의 **PG 환불은 실제로 호출하지 않는다**. `compensating_transaction_failures`에 `PG_REFUND_CALL`로 기록만 남기고, 실제 회수는 `[2차]` 환불 도메인이 수행한다. `PgPort`에 `refund`가 없다.

**맥락.** 분할 결제에서 카드 청구는 성공했는데 TX2(확정)가 실패하면, 이미 청구된 카드를 되돌려야 정합성이 맞다. 하지만 PG 환불은 그 자체로 또 하나의 외부 호출(실패·타임아웃 가능)이다.

**근거.** 내부 잔액·한도 원복은 단일 로컬 트랜잭션이라 안전하다([[D-02]]). 반면 PG 회수는 환불 한도·중복 환불 방지·PG별 정책 등 **환불 도메인 고유의 복잡도**를 끌어온다. 1차 스코프(결제 본체)에 이를 넣으면 경계가 무너진다. 따라서 **회수 의무를 기록으로 영속화**해 두고(유실 없이), 회수 실행은 환불 도메인으로 위임한다.

**대안.** ① payment-core에서 즉시 PG 환불 호출 — 환불 도메인 로직이 결제 본체로 누수, 또 다른 외부 호출 실패 모드 추가. ② 기록도 없이 무시 — 청구된 카드를 영구히 못 되돌림(금전 정합성 붕괴).

**영향.** spec 1장 out-of-scope, 10장 R-22/R-23, 부록 1번에 일관 표기. v0_2 시나리오22의 "PG 환불 먼저" 흐름과 **의도적으로 다름**(차이를 명시). [[payment-core-scope]] 메모리와 연결. `[2차]` 환불 도메인이 이 기록 테이블을 입력으로 회수.

## D-10 — 충전 잔액 증가 = TX2(PG 성공 후), 한도 무관

**결정.** 충전은 TX1에서 멱등성·`charges` 행만 PENDING으로 만들고(잔액 변화 없음), **PG 청구 성공 후 TX2에서 잔액을 증가**시킨다. 충전은 일일 한도에 영향을 주지 않는다.

**맥락.** 충전은 "외부 수단으로 잔액을 채우는" 흐름이라 결제와 자금 방향이 반대다. 결제는 먼저 차감 후 PG 청구(실패 시 원복)지만, 충전은 PG가 실제로 돈을 받아야 잔액을 늘릴 수 있다.

**근거.**
- **PG 성공 후 증가** — PG 청구가 실패했는데 잔액을 먼저 늘리면 공짜 잔액이 생긴다. 따라서 증가를 TX2(성공 확인 후)에 둔다. **PG 거절 시 보상 자체가 불필요**(아직 안 늘렸으므로) → 결제보다 단순.
- **한도 무관** — 일일 한도는 **결제(지출) 사기 방지** 장치다(INV-3). 충전은 지출이 아니라 적립이므로 누적 대상이 아니다.

**대안.** 결제처럼 TX1에서 미리 증가 후 PG 호출 — PG 실패 시 잔액 원복 보상이 필요해 불필요하게 복잡(이득 없음).

**영향.** 타임아웃은 결제와 동일하게 보정 배치 위임([[D-08]]): 성공 확인 시 잔액 증가+COMPLETED, 실패 확인 시 FAILED(보상 없음). 충전 후 즉시 결제는 같은 사용자 락으로 자연 직렬화([[D-03]]).

## D-11 — Kafka 파티션 키 = user_id

**결정.** `payment-created`·`balance-charged` 이벤트의 파티션 키를 `user_id`로 한다.

**맥락.** 다운스트림(정산·리워드·가맹점 웹훅)은 한 사용자의 이벤트를 **발생 순서대로** 받아야 잔액/적립 계산이 맞다. Kafka는 **같은 파티션 안에서만** 순서를 보장한다.

**근거.** 키를 `user_id`로 잡으면 한 사용자의 모든 이벤트가 같은 파티션에 떨어져 **사용자별 순서**가 보장된다. 동시에 사용자 단위로 파티션 분산돼 처리량도 확보.

**대안.** ① `payment_id`/`charge_id` 키 — 건별 고유라 같은 사용자 이벤트가 다른 파티션으로 흩어져 순서 깨짐. ② 키 없음(라운드로빈) — 순서 보장 전무.

**영향.** 프로듀서 `acks=all` + `enable.idempotence=true` + manual commit(at-least-once). 발행 실패는 `kafka_publish_failures` 적재 후 재발행 배치(1분)가 전파(결과적 일관성).

## D-12 — payments에 user_id 컬럼 보유

**결정.** `payments` 테이블에 `user_id` 컬럼을 둔다.

**맥락.** 결제는 잔액·한도(둘 다 `user_id` 키)와 엮이고, 이벤트 파티션 키([[D-11]])·사용자별 조회·감사에도 user_id가 필요하다.

**근거.** `user_id`가 **결제·잔액·한도·이벤트를 잇는 핵심 키**다. payments에 직접 두면 조인 없이 사용자 귀속을 즉시 알 수 있고, 멱등성 `(user_id, key)`·이벤트 키·`balance_history` 연결이 자연스럽다.

**대안.** order_id로만 식별하고 user_id는 멱등성/주문 테이블에서 역추적 — 매 조회마다 조인, 이벤트 파티셔닝에 불리.

**영향.** spec 3-1. 멱등성·이벤트·감사 로그가 이 컬럼을 공유.

## D-13 — 잔액 음수 방지는 앱 레벨 불변식 (Money + UserBalance)

**결정.** 잔액이 음수가 되지 않도록 **애플리케이션 도메인 불변식**으로 막는다(INV-2). 차감 시 `잔액 ≥ 차감액`이 아니면 `INSUFFICIENT_BALANCE`로 거부하고 상태를 바꾸지 않는다. `Money`(음수 차감 금지) + `UserBalance.deduct`가 강제한다.

**맥락.** 잔액 음수는 곧 "없는 돈을 쓴 것"이라 절대 허용 불가. DB CHECK 제약으로 막을 수도, 앱에서 막을 수도 있다.

**근거.** 비관적 락([[D-03]]) 안에서 `FOR UPDATE`로 최신 잔액을 읽은 뒤 **도메인이 차감 가부를 판정**하면, 음수 진입 자체를 막으면서 사용자에게 **명확한 에러 코드**(INSUFFICIENT_BALANCE)를 줄 수 있다. DB CHECK는 위반 시 SQL 예외만 던져 도메인 의미를 잃는다. 불변식을 도메인(`UserBalance`)에 두면 규칙이 한 곳에 응집.

**대안.** ① DB CHECK(balance >= 0) 단독 — 제약 위반 예외를 앱이 다시 도메인 에러로 번역해야 함, 표현력 부족. ② 검증 없이 차감 후 음수면 롤백 — 경합·복잡도 증가.

**영향.** validation 단계 + 락 안 재확인 2중. `Money`(INV-1, [[D-15]])가 음수/음수차감을 값객체 수준에서 1차 차단. 충전(잔액 증가)엔 음수 위험 없음.

## D-14 — 일일 한도는 lazy 자정 리셋 (배치는 보조)

**결정.** 일일 한도 누적(`user_daily_usage.used_amount`)은 결제·원복 시점에 `last_reset_date < 오늘`이면 **0으로 되돌린 뒤 진행**한다(lazy reset, INV-7). 자정 배치 리셋은 보조 수단이며 **정확성은 lazy 리셋이 보장**한다.

**맥락.** 일일 한도는 매일 0시에 초기화돼야 한다. 자정에 전체 사용자를 배치로 리셋하는 방법과, 접근 시점에 날짜를 비교해 리셋하는 방법이 있다.

**근거.** 자정 배치는 ① 대상이 수백만 행이면 무겁고 ② 배치 지연/실패 시 그 틈에 들어온 결제가 **전날 누적**으로 한도를 계산하는 정합성 구멍이 생긴다. lazy 리셋은 **그 사용자가 실제 결제하는 순간** 날짜를 비교해 리셋하므로, 배치 상태와 무관하게 항상 정확하다. 배치는 "오래 안 쓴 사용자 행 정리" 정도의 보조.

**대안.** ① 자정 배치 단독 — 위 정합성 구멍 + 대량 업데이트 부하. ② 한도 테이블에 날짜 파티션 — 1차 규모엔 과설계.

**영향.** 결제·보상 양 경로가 진입 시 lazy 리셋을 거친다. `last_reset_date` 컬럼으로 판정. 배치 실패가 정확성에 영향 없음(가용성 보조일 뿐).

## D-15 — 금액 = 원 단위 정수(long) 값객체 Money

**결정.** 모든 금액은 **원 단위 정수**(`long`)로 표현하고 `common/Money` 값객체로 다룬다(INV-1). 음수 금지, 음수가 되는 차감 금지를 값객체가 강제. DB는 `BIGINT`.

**맥락.** 금액 연산에 부동소수점을 쓰면 반올림 오차가 누적돼 정산이 틀어진다. 원화는 최소 단위가 1원이라 소수가 없다.

**근거.** 정수(long) 원 단위는 **오차가 없고** 비교·합산이 단순하다. 값객체로 감싸면 "음수 금액", "잔액보다 큰 차감" 같은 불변식을 **타입 수준에서 한 번에** 강제해 도메인 곳곳의 방어 코드를 없앤다. long 범위(약 9.2×10^18)는 원화 금액에 충분.

**대안.** ① `double`/`float` — 부동소수점 오차, 금융 부적합. ② `BigDecimal` — 정확하지만 원 단위 정수엔 과하고 연산·비교가 장황. ③ 원시 long 직접 사용 — 불변식이 흩어져 음수/오용 방지 누락 위험.

**영향.** 도메인 전반(잔액·한도·allocation·충전)이 `Money`로 통일. INV-1로 spec 2장에 단일 정의, INV-2([[D-13]])·INV-3 등이 이 위에 성립. 다통화는 본 스코프 밖(단일 통화 가정).

## D-16 — PG 멱등키는 결제당 base 1개 + allocation별 파생

**결정.** `payment_idempotency.pg_idempotency_key`는 **결제당 base 키 1개**(reserve에서 생성, `markPgCalling`에서 commit). 실제 PG 청구 시점에 외부 allocation마다 **`{base}:{allocationId}`로 파생**해 `PgPort.charge`에 전달한다. base 키 자체로는 PG를 호출하지 않는다.

**맥락.** 분할 결제는 외부 수단(CARD/ACCOUNT)이 2개 이상일 수 있고, 각 외부 allocation은 **별도의 PG 청구**다. base 키 하나를 모든 청구에 그대로 보내면 PG가 두 번째 청구를 첫 번째의 **중복 재시도로 디듀프**해 한 건만 청구되는 정합성 붕괴가 생긴다.

**근거.**
- **파생 = `{base}:{allocationId}`** — `allocation.id`가 UUID로 외부 청구마다 유일하고 `payment_allocation`에 영속된다. 따라서 파생 키는 **청구마다 유일**(디듀프 충돌 없음), **재시도에 안정**(같은 allocation 재호출 시 동일 키), **보정 배치가 재구성 가능**([[D-08]]: base는 멱등성 행, allocation id는 allocation 행에서 읽어 결합).
- **결제당 base 유지** — 스키마(`pg_idempotency_key` 단일 컬럼)를 그대로 쓰고, allocation별 키 컬럼을 추가하지 않는다(파생은 결정적이라 저장 불필요).

**대안.** ① base 키 하나를 모든 allocation 청구에 공유 — 외부 다중 수단에서 PG 디듀프로 누락 청구(기각). ② allocation별 키를 `payment_allocation`에 별도 저장 — 결정적 파생이면 중복 데이터. ③ `allocationId`를 그대로 PG 키로 사용 — 내부 ID 노출·키 로테이션 불가, base 결합이 더 안전.

**영향.** 파생 로직은 호출부(오케스트레이터 `ProcessPaymentService` + `PgPort.charge`)가 생기는 **다음 태스크에서 TDD로 구현**한다(현 스코프엔 호출자 없음 → 코드 보류). 도메인 `PaymentIdempotency.pgIdempotencyKey`(base)와 `Reservation.externalAllocations`(allocation id)가 파생에 필요한 입력을 이미 보유. plan.md의 "동일 `r.pgIdempotencyKey()`를 루프 전체에 전달"은 본 결정으로 대체.

## D-17 — confirm(TX2) 일시적 실패는 재시도, 소진 시 보상 대신 보정 배치로 완결

**결정.** 오케스트레이터는 `confirm`이 **일시적 데이터 접근 예외**(`TransientDataAccessException`: 커넥션 순단, 데드락 희생, 쿼리 타임아웃)로 실패하면 **짧은 백오프로 총 3회까지 동기 재시도**한다. 재시도가 **소진되면 보상하지 않는다** — DB 발자국(`payment_idempotency.status=PENDING` + `pg_call_status=SUCCESS`, `payments.status=PENDING`)을 그대로 두고 `INTERNAL_ERROR`(500)로 응답하며, **보정 배치가 이 조합의 행을 쓸어 confirm을 재구동해 PAID로 완결**하고 payment-created 이벤트도 그때 발행한다. **결정론적 실패**(도메인 가드 위반 등 비일시적 예외)만 재시도 없이 즉시 보상한다(FAILED_REFUNDED + 회수 기록 — 시나리오 22 원안은 이 경로로 한정).

**맥락.** confirm 시점은 PG 청구가 **이미 성공한 뒤** — 남은 일은 "우리 DB에 성공을 기록"뿐이다. 여기서 보상을 택하면 일시적 순단 한 번이 "환불 빚 + 2차 도메인 회수 + 고객에게 실패 통보(카드값은 나갔다 돌아옴)"로 확대된다. 또한 기존 설계는 **정보가 더 적은** 타임아웃(청구 여부 미상)은 배치에 맡기면서, **정보가 더 많은** confirm 실패(청구 성공 확실)는 되돌리는 비대칭이 있었다. 청구 성공이 확실하므로 PAID 수렴이 유일하게 옳은 종착이고, 배치가 그 수렴을 보장한다.

**근거.**
- **재시도는 안전** — 실패한 confirm 트랜잭션은 롤백돼 있어 같은 인자로 재실행해도 이중 정산이 없다. 동기 3회·백오프 100ms(최악 +200ms)는 살아나는 경우 고객이 즉시 확정 응답을 받게 한다.
- **DB 발자국이 곧 내구성 있는 큐** — `pg_call_status=SUCCESS + status=PENDING` 조합 자체가 "청구됐는데 확정 못 함"을 유일하게 식별한다. 별도 재시도 이벤트를 발행하면 그 발행이 같은 장애에 물리고(재귀 복구 문제) 새 인프라가 필요하다.
- **고객 UX가 타임아웃과 일관** — 500 수신 → 같은 키 재시도는 PENDING이라 409(이중결제 방지) → 배치 확정 후 REPLAY로 결과 수신. 새로운 상태 표면이 생기지 않는다.
- **일시적 예외로 한정** — 결정론적 실패는 배치가 재구동해도 영원히 같은 가드에 걸린다. Spring 예외 위계(`TransientDataAccessException`)가 분류를 제공한다.

**대안.** ① 재시도 소진 시 즉시 보상 — 일시 장애마다 환불 빚 발생, 타임아웃 처리와 비대칭(기각). ② Kafka 이벤트 발행으로 비동기 재시도 트리거 — 발행 자체가 같은 장애에 노출, DB 발자국으로 충분(기각). ③ 동기 무한 재시도 — 응답 지연 상한 없음(기각). ④ Spring Retry 의존성 — 루프 하나에 과함(기각).

**영향.** 오케스트레이터의 confirm 예외 처리 2분기: transient 소진 → 발자국 유지 + `INTERNAL_ERROR` / 비일시적 → 즉시 compensate(FAILED_REFUNDED) + `INCONSISTENT_STATE`. **보정 배치([[D-08]]) 요구사항 추가**: `SUCCESS+PENDING` 행의 confirm 재구동(+이벤트 발행)과, 반복 실패 시 포기 상한(그때 최후 보상+회수 기록) — 상한 정책은 배치 태스크에서 확정. 배치 구현 전까지 해당 행은 PENDING에 머문다(타임아웃·서버 사망과 동일한 기존 공백).

## 부록. v0_2 대비 변경·해소된 모순

본 ADR이 v0_2에서 **명시적으로 바꾼** 지점.

1. **lock wait timeout 3초 → 1초** — v0_2 본문 3초와 9-4 보강이 충돌. 보강(1초) 채택([[D-07]]). docker-compose의 `innodb_lock_wait_timeout`도 1초로 일치시킬 것.
2. **PG 회수 흐름** — v0_2 시나리오22는 "보상 시 PG 환불 먼저". 본 스코프는 **회수 보류·기록만**으로 변경([[D-09]]). 실제 회수는 `[2차]`.
3. **확장 전략(TPS 1000/10000)** — v0_2의 확장 논의는 1차 구현 진실이 아니므로 spec에서 분리, 본 문서 영향란·spec 부록으로 이월.
