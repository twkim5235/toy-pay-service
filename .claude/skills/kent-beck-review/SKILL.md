# 켄트 백 스타일 코드 리뷰

현재 브랜치/스테이징 변경을 켄트 백의 원칙으로 검토한다. 핵심 정신: **작동하게 만들고, 올바르게 만들고, 빠르게 만든다 (그 순서로).** 작은 단계, 테스트가 설계를 이끈다.

## 1. 변경 수집
```bash
git diff main...HEAD          # 브랜치 전체 변경 (또는 git diff --staged)
git diff --stat main...HEAD
```
프로덕션 코드와 **테스트를 함께** 본다.

## 2. 리뷰 렌즈 (우선순위 = 평가 순서)

### A. 단순 설계 4규칙 (이 1→4 순서가 곧 우선순위)
1. **테스트를 통과하는가** — 동작이 검증되는가? 테스트가 존재하고 그린인가?
2. **의도를 드러내는가** — 이름·구조가 "무엇을·왜"를 말하는가? 주석 없이 읽히는가?
3. **중복이 없는가** — 지식(결정)의 중복(DRY). 같은 규칙이 여러 곳에 흩어졌는가?
4. **요소가 최소인가** — 불필요한 클래스·추상화·옵션·매개변수가 없는가? (YAGNI)
> 규칙끼리 충돌하면 상위 규칙이 우선.

### B. Tidy First — 구조 변경 vs 동작 변경 분리
- 한 변경(커밋/PR)에 **리팩터(구조)와 기능(동작)이 섞였는가?** 섞였으면 분리를 제안.
- 구조 변경은 동작을 바꾸지 않아야 한다(테스트 그대로 그린).

### C. 작고 안전한 단계
- 변경이 작고 되돌리기 쉬운가? 한 번에 너무 많이 바꾸지 않았는가?
- 각 커밋이 그린 상태(Red→Green 단위)인가?

### D. 테스트 품질 (Beck은 테스트를 설계 도구로 본다)
- 테스트가 **행위/의도**를 말하는가 (구현 디테일에 결합되지 않았는가)?
- 경계·실패 경로를 덮는가? 테스트가 설계를 이끌었는가, 사후 추가인가?

### E. 결합도·응집도·이름
- 모듈 경계(헥사고날: domain ↔ application ↔ adapter)가 지켜지는가?
- 이름이 의도를 드러내는가 — SQL/인프라 용어가 도메인·포트로 새지 않았는가?

## 3. 보고 형식
- 발견을 **단순설계 4규칙 우선순위 순**으로 정리.
- 각 항목: `파일:라인` + 무엇이/왜 + **작은 단계로의** 개선 제안.
- 잘 된 점도 명시 (좋은 작은 단계·드러난 의도는 인정).
- **블로킹**(동작/테스트 깨짐, 1번 위반) vs **권고**(스타일·구조)를 구분.

## 이 프로젝트 맥락에서 함께 본다
- 의존 규칙(adapter→application→domain), 포트의 의도 명명, JPA 엔티티 package-private 캡슐화, Lombok 범위(adapter/app만), 도메인 순수성 — 이 규약 위반은 "의도를 드러내는가 / 요소 최소 / 결합도" 렌즈로 평가한다.
